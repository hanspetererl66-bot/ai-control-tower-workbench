## Databricks-Demo für SAP TechEd (Stand 03.11.2026, alles auf `main`; Angleichung der Gesellschaftscodes in PR #171)
- Ordner `examples/databricks-demo/` (README ist die Anleitung): vier Szenarien als Goose-Recipes (`recipes/`) und gleichlautende Skills (`skills/`, erzeugt mit `npm run sync:databricks-demo`, nicht von Hand ändern): Margin-Analyst (Genie), Pipeline-Bereitschaft, PO-Verzugsrisiko mit Expedite, Finance Pre-Close (offene GR/IR-Posten, Intercompany-Differenzen, Rückstellung). Seed-SQL `sql/` (`all-in-one.sql` = 00 bis 07, Governance 08 und Grants 09 getrennt), Daten deterministisch aus `seed/data.mjs` und `connectors/sap-mock/server/data.mjs`.
- Zwei Wege zu Databricks: Connector `databricks` (REST, Zugriffstoken, Genie und nur lesendes SQL) und Brücke `databricks-mcp` (`connectors/databricks-bridge`, stdio zu den verwalteten MCP-Endpunkten, OAuth-Service-Principal). Die Recipes laufen mit beiden; ohne die typisierten Funktions-Tools rufen sie die Unity-Catalog-Funktionen über das SQL-Tool auf.
- Mock-SAP `connectors/sap-mock`: Schreiben nur zweistufig (`draft_*`, dann `submit_draft` mit Token und `confirmed=true`), auch für Rückstellungen (`draft_accrual_posting`, begrenzt auf den offenen GR/IR-Wert).
- Installieren: `npm run databricks-demo:load` (Daten) und `npm run install:databricks-demo -- --host <workspace>` (Skills und Erweiterungen in `goose-home`, ohne Secrets; die Konfigurationsdatei danach nicht committen).

Abgesehen vom Zugang: Test-Workspace war eine Demo-Version, Service Principals dort möglicherweise eingeschränkt.

## SAP S/4HANA Sandbox (Stand 04.11.2026, Branch `feat/sap-sandbox`)
- Connector `connectors/sap-sandbox` (nur lesend, Einzel-Connector wie notion; Bundle `npm run build:sap-sandbox-mcpb`): OData V2 gegen `https://sandbox.api.sap.com/s4hanacloud` mit dem persönlichen API-Key (Header `APIKey`, Secret `SAP_API_KEY`, nur an `sandbox.api.sap.com`, andere Basis-URL wird abgelehnt). Werkzeuge: `sap_sandbox_check_connection`, `_list_apis`, `_list_entity_sets`, `_query`, `_get`, dazu die zwei Use Cases `_o2c_scan`, `_order_to_cash` und `_customer_360`. Reine Logik in `connectors/sap-sandbox/server/o2c.mjs` (Stufe, Lücke, Kunden-Kennzahlen), Tests `sap-sandbox-connector`, `sap-sandbox-o2c`, `sap-sandbox-snapshot`, `cognee-sap-corpus`.
- Use Cases (von Hans-Peter gewählt): **Order-to-Cash-Trace** (Auftrag, Lieferung, Warenausgang, Faktura; "geliefert, nicht fakturiert") und **Kunde 360 im Wissensgraph**. Schnappschuss: `SAP_API_KEY=... npm run sap-sandbox:snapshot` prüft zuerst, welche APIs die Sandbox wirklich anbietet, und schreibt `examples/sap-sandbox/snapshot.json` (git-ignoriert); `npm run cognee:corpus` macht daraus zusätzlich `dist/cognee-corpus-sap.json` (`connectors/_lib/server/cognee-sap-corpus.mjs`, Kennungen `sap-customer:`, `sap-order:`, `sap-delivery:`, `sap-invoice:`, `sap-material:`), einspielen ohne `--reset`: `.venv-cognee/bin/python scripts/cognee-seed.py --corpus dist/cognee-corpus-sap.json`. Anleitung: `examples/sap-sandbox/README.md`.
- **Nicht getestet:** alles nur mit Fake-`fetch` (die Cloud-Sandbox erreicht `sandbox.api.sap.com` nicht, Proxy 403). Entity- und Feldnamen (`ReferenceSDDocument`, `OverallDeliveryStatus`, `OverallOrdReltdBillgStatus`, `BillingDocumentIsCancelled` u. a.) folgen dem SAP API Business Hub und sind **nicht gegen die echte Sandbox geprüft**; welche APIs die Sandbox anbietet, zeigt erst der Schnappschuss-Lauf. Cognee-Seed mit den SAP-Dokumenten und die Electron-App ungetestet.
- **Grenzen:** Sandbox-Daten sind fest (nichts anlegen, nichts ändern). Zahlungsverhalten steckt nicht in den Vertriebs- und Faktura-APIs (bräuchte Offene Posten oder Ausgleichsdaten). Spaces haben kein Netzwerk: ein Space kann Sandbox-Daten nur über eine feste Brücken-Anfrage der App zeigen (Muster `predict_late_payments` im Sales-Space), nicht direkt. Der Renewals-Space baut auf Sub4Me-Verträgen und Angeboten (Abonnementdaten), die S/4 so nicht hat; Sales-Pipeline und Forecast sind CRM-Daten, nicht S/4.
